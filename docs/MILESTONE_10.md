# Milestone 10 — Stripe test-mode initial payment

**Status:** Backend-only synthetic portfolio workflow. The code accepts only Stripe test credentials and test-mode provider objects. No live payment, public booking acceptance, guest account, email delivery, balance Checkout, cancellation charge, or refund execution is enabled.

## Provider setup and boundaries

The official `stripe` Node SDK is pinned to `22.6.2`, with API version `2026-08-26.dahlia` in `src/server/stripe-adapter.ts`. Set `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_ACCOUNT_ID`, `STRIPE_SUCCESS_URL` and `STRIPE_CANCEL_URL` from one **test** account in local environment only. The adapter rejects live secret keys, live Session/PaymentIntent/Event objects, account mismatch and non-HTTPS return URLs outside localhost. Its account check retrieves the configured Stripe account before provider API operations. Webhook signature verification uses the SDK default timestamp tolerance.

The Checkout request is `mode=payment`, explicit card-only, one EUR integer-cent line item equal to the accepted INITIAL obligation, no promotion codes and no automatic tax. Booking, hold, attempt and command IDs appear in the Session and PaymentIntent metadata. Stripe's `expires_at` must be at least 30 minutes in the future when Stripe receives the request, so the worker adds a 30-second transport allowance to the 30-minute target. It records and uses the returned Session creation and expiry timestamps; validation rejects a returned duration outside 29–31 minutes. The return URLs are navigation only and never credit a payment.

## Durable command and recovery

`dispatchSessionCreate` is for a trusted internal worker. Its short database transaction locks the acceptance context and financial/inventory parents, records exact request parameters, first submission, lease owner, monotonically increasing generation and attempt count, then commits **before** the Stripe POST. The API call has a stable command idempotency key and occurs outside any database transaction. A successful open, unpaid Session is stored with its ID, URL and authoritative timestamps before the URL is returned; attempt and hold become `OPEN` and `ACTIVE` only while the original blocking claim remains. A Session already completed or expired when the create response arrives is stored as `RECONCILING` and is handled by current-object retrieval.

Lost responses become `UNKNOWN` and keep the claim blocking. A verified Session webhook supplies only a locator: reconciliation retrieves the current Session, validates the account, test mode, accepted amount/currency, client reference and complete booking/hold/attempt/command metadata, then binds its ID under the original acceptance locks. A PaymentIntent-only event uses Stripe's Checkout Sessions list filter for that PaymentIntent, then retrieves and validates the matching current Session. The existing unique Session-ID index prevents two attempts from owning one Session. Binding records reconciliation and audit evidence, resolves the command without clearing its first-submission or lease-generation history, and fences any late original worker response. Payment confirmation still requires current Session, PaymentIntent and captured-charge evidence. Failed lookup never authorizes another create or releases the claim.

A later command worker replays the exact persisted operation only within 24 hours of the first submission. At that boundary, missing submission chronology, or an unsafe command state, it quarantines the command for investigation. A subsequent verified webhook can still recover the **existing** Session after quarantine. `dispatchDueSessionCommands` and `sweepInitialAttempts` are bounded internal entry points. They need a trusted process or job runner; no public worker endpoint or scheduler has been provisioned. Unresolved/quarantined commands require operational monitoring and manual investigation. A lease timeout alone never releases inventory.

## Webhook and reconciliation

`POST /api/stripe/webhook` reads at most 1 MiB of the raw request body, verifies the Stripe signature, test mode and account, then durably inserts the Event ID, object identity, timestamp and SHA-256 digest before returning 200. Invalid input returns 400; storage failure returns 503 for provider retry. Duplicate Event IDs increment a delivery counter. The route performs no provider retrieval or financial transition. Unexpected asynchronous-payment events are quarantined; unknown event types are recorded and ignored.

`processWebhookInbox` atomically claims one due row at a time with `FOR UPDATE SKIP LOCKED`, a two-minute lease and an owner fence. A concurrent worker cannot claim the same live lease. Unresolved and failed items receive a controlled error code and exponential retry delay starting at 30 seconds. After five failed processing attempts they enter durable `INVESTIGATE`; an expired fifth lease also reaches that state on the next worker run. Investigation requires an authorized operator to review provider state and reschedule or resolve the row. Event IDs and payload digests remain durable; failed events are never deleted or silently acknowledged as processed.

The inbox resolves the attempt by Session ID or PaymentIntent metadata, then calls `reconcileInitialAttempt`. A webhook payload is only a pointer: reconciliation retrieves the current Session and linked PaymentIntent/charge from Stripe. It requires test mode, expected account, full booking/hold/attempt/command correlation, exact EUR amount, `payment_status=paid`, succeeded PaymentIntent and paid/captured charge evidence. Missing, conflicting or in-progress evidence leaves the original claim blocking and the attempt/hold reconciling. Out-of-order and duplicate events are safe because current provider objects and unique database keys decide the result.

For a verified initial capture, one transaction inserts a unique payment record and initial-obligation allocation, marks the attempt `SUCCEEDED`, transfers the **same** inventory claim from hold to booking while retaining `origin_hold_id`, consumes the hold, confirms the booking, writes redacted reconciliation/audit evidence and queues a logical guest confirmation notice. A 30% initial payment leaves the existing BALANCE obligation outstanding; a 100% initial payment covers the accepted total. No external notification delivery is implemented.

An open unpaid, unexpired Session can restore `OPEN`/`ACTIVE`. Expiration calls occur outside the database transaction, followed by another current-provider read. A terminal expired/unpaid Session with no successful or processing PaymentIntent can release the claim and expire the booking atomically. An unknown response, authentication in progress, missing provider truth or elapsed hold time alone cannot release inventory. If a captured payment appears after safe release or after the claim becomes unavailable, reconciliation creates exactly one `UNALLOCATABLE` payment record, incident, full refund obligation, audit event and operations notice. It does not resurrect the booking or displace a competing claim. Actual refunds belong to Milestone 13.

## Database changes and guarantees

Migration `0017_stripe_initial_fields.sql` adds `checkout_url` to the existing attempt and `request_params` to the existing provider command. They allow a committed, exact Checkout request and a committed return URL without creating new payment tables.

Migration `0018_stripe_initial_guards.sql` advances the Milestone 9 provisional accepted-booking guards for verified confirmation and provider-evidenced terminal release. It permits hold-to-booking transfer only when the original claim and hold match a succeeded initial attempt with allocated payment; it checks pending, confirmed and expired aggregates at commit. It preserves accepted owner immutability, release proof, monotonic command evidence and the Milestone 9 pre-dispatch abandonment path. A deferred initial-credit check requires an accepted allocated payment record to match its attempt, obligation and full allocation. The migration grants the runtime role only the additional table-specific SELECT/INSERT privileges needed for payment, reconciliation, incident, refund-obligation and notification records, plus scoped webhook inbox writes. Schema ownership and DDL remain with the migration role. Existing 28 tables, accepted snapshots, historical fixture compatibility, allocation budget serialization and the single GiST inventory exclusion constraint remain intact.

Migration `0019_webhook_recovery_inbox.sql` adds processing-attempt count, next retry time, lease owner/expiry and controlled last-error fields to the existing webhook event table. A row-local check constrains processing states, nonnegative attempts, lease pairing and error-code length; a partial due-work index supports bounded claiming. No new table or broader runtime privilege is needed. Migration `0017` and `0018` remain unchanged.

These database checks establish consistency of committed local evidence. PostgreSQL cannot independently authenticate Stripe responses; provider truth and account identity are checked by the server adapter and reconciliation service. Worker credentials and runtime database access must remain restricted to trusted server processes. Webhook signing secrets and raw payloads are not stored in the inbox.

## Local verification and operations

Run migrations with `MIGRATION_DATABASE_URL`; the runtime uses `DATABASE_URL`. For local Stripe CLI testing with test credentials, forward signed test events to `http://localhost:3000/api/stripe/webhook` and put the CLI-provided `whsec_...` into the local environment. The internal command, inbox and reconciliation functions must be invoked by a trusted test/job process; the webhook route deliberately does not dispatch them. Test credentials were unavailable in this implementation environment, so deterministic provider fixtures and real PostgreSQL tests verify the provider boundary without claiming a live Stripe round trip.

The PostgreSQL tests cover exact request correlation, replay, fencing, unknown outcomes, 24-hour quarantine, signature/timestamp/mode rejection, duplicate and out-of-order events, lost-response recovery from signed Session and PaymentIntent events, wrong-account/amount/correlation rejection, concurrent one-time credit and inbox claiming, atomic transfer, 30% and 100% initial splits, rollback/replay, open recovery, terminal unpaid release, uncertain blocking, scheduled retries/investigation, late unallocatable capture and direct SQL rejection. The final handover records the exact test counts and migration results on both the existing development and fresh test databases.

Operations should alert on quarantined commands, persistent `RECONCILING` holds, webhook retries/quarantine, provider identity mismatch, and unallocatable captures/refund obligations. Milestone 11 must implement the separately authorized balance-payment flow and its deadlines. Later work must add trusted scheduling, external notification delivery, actual refunds, guest access and the security/concurrency acceptance gates from the implementation plan. No inference from a browser return or from time alone may settle a booking.
